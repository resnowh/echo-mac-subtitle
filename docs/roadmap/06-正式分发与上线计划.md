# 06 正式分发与上线计划

> v3：当前仅执行 Mac/Windows 分发要求。Android/iOS 渠道、四端 R0～R6 排期、M01～M10 移动门槛均为延后参考，不阻塞桌面发布。用户没有 iOS 手机，无需为本阶段取得 iOS 测试设备；当前排期与验收以 [07](07-Mac优先的桌面实施方案.md) 为准。

版本 v2｜2026-09-16｜首期个人/小范围 BYOK；未申请账号、生成证书、付费或上传安装包。

## 1. “具备真实上线能力”的完成定义

必须实际拿到并验证：可复现的 Release 构建、有效签名、非开发机安装、上一版本升级、旧档与凭据策略、故障恢复、可用发布说明和维护流程。只是有源码、能调试运行或有一个未签名压缩包均未完成。

按平台记录两类里程碑：**签名测试可分发**与**长期正式渠道可分发**。iOS 的 TestFlight 只完成前者；只有取得相应正式渠道批准并可安装后，才记录后者。审核是否通过由平台决定，本方案不能保证结果。

## 2. 首期分发路线

| 平台 | 小范围测试 | 长期版本推荐 | 必要依赖与检查 |
|---|---|---|---|
| Windows | 签名 MSIX，测试证书需在测试机显式信任 | 受信任签名 MSIX 或 Microsoft Store，择可用渠道 | 发布者身份稳定、证书资格与有效期、干净机器安装、升级；签名不保证完全没有信誉提示 |
| macOS | 已签名测试包 | Developer ID 签名 + notarization 的 app/DMG | Apple 账号权限、Hardened Runtime/适当 entitlement、第三方库签名、公证结果与票据验证 |
| Android | Release 签名 APK | 小范围可继续签名 APK；后续上 Play 则增加 AAB 与商店流程 | 稳定 applicationId、versionCode、签名密钥与备份；覆盖安装保留档案 |
| iOS | TestFlight；或注册测试设备后的 Ad Hoc | App Store，或获批准的 Unlisted 链接分发 | Apple Developer Program、Bundle ID、证书/profile、审核、真机与更新验证 |

参考：[MSIX 签名](https://learn.microsoft.com/en-us/windows/msix/package/sign-msix-package-guide) · [Mac Developer ID](https://developer.apple.com/developer-id/) · [Android 签名](https://developer.android.com/studio/publish/app-signing)

### iOS 分发不能省略的区别

- TestFlight 构建有 90 天可用窗口，外部测试流程涉及 Beta 审核，需持续维护新构建。[TestFlight](https://developer.apple.com/testflight/) · [构建有效期](https://developer.apple.com/help/app-store-connect/reference/app-uploads/app-build-statuses)
- Ad Hoc 需要登记设备并受设备数和 provisioning profile 有效期限制，不是向任意用户长期发送 IPA 即可安装。Apple 当前按会员年度和设备系列设置注册数量上限。[设备限制](https://developer.apple.com/help/account/devices/devices-overview)
- Unlisted 是正式 App Store 分发方式，需正常审核并申请批准，适合有限受众评估；链接隐藏不等于访问控制，获得链接的人仍可能安装。若不获批准，应按适用渠道调整，不能把它当作必然可用的私有商店。[Unlisted](https://developer.apple.com/support/unlisted-app-distribution/)

用户尚未确认上架地区、账号类型和既有资质。首期不默认承诺中国区、海外所有地区或任一具体商店审核结果；在正式提交前补齐发布地区、身份及当地服务可用性核查。

Android 直接发 APK 也需要跟踪开发者验证政策，不能永久假定“商店外分发不需要注册”。本次官方页说明相关要求按地区和时间分阶段推出，并提供小范围分发路径；发布时按目标设备、地区和渠道核查适用流程。[Android 开发者验证](https://developer.android.com/developer-verification)

## 3. BYOK 首期需要什么，不需要什么

### 首期实现

- Soniox Key 的添加/校验/替换/删除；DeepSeek Key 可选；网络和额度错误说明可操作。
- 本地安全存储，不进源码、发行包、日志、Archive 或共享导出。不要收集测试用户 Key。
- 用户可查看服务商、音频/文本流向、自动保存内容与删除方式。默认不落盘原始音频。
- 默认本地存档；一键导出/导入，应用内删除存档并明确本地备份的处理。
- 不添加开发者自有数据分析 SDK 作为发布前置条件；崩溃诊断默认脱敏，分享前预览。
- 应用费用与第三方 API 费用分别说明。首期应用定价尚未确定，不擅自加入订阅或购买链接。

### 以后提供统一服务才新增

账户、订阅、服务端计量/限额、防滥用、退款状态、后端密钥代理或短期凭据、云同步与删除流程。Soniox 有临时 Key 机制可供后续使用，但首期 BYOK 无需搭一个服务器只为转发用户 Key。[Soniox 临时 Key](https://soniox.com/docs/guides/temporary-api-keys)

## 4. 审核与发行材料

正式渠道准备隐私政策/支持页面、联系邮箱、截图/图标、功能和平台限制说明、版本记录、权限用途描述、适用的隐私披露与开源许可证。政策披露以实际数据流和服务商 SDK 为准，不能因为“不建后端”就填写“不发送数据”。

Apple 提交需保证审核能体验主要功能：准备专供审核的可控测试凭据或可审查演示路径，并给出操作步骤；不要把永久测试 Key 硬编码进公开包。录音应取得明确同意并可见；后台模式用于真实录音。BYOK 的审核方式、定价和外部购买引导必须按选定地区及届时规则核查，不预先保证免审或免支付规则。[App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)

若后续上 Google Play，补齐 Data safety、目标 API、前台服务申报、账号验证和相应测试要求。新个人账号可能需满足封闭测试及生产权限申请；本轮查询的规则对适用账号要求至少 12 位测试者连续加入 14 天，不能只把 APK 签好就视为满足 Play 上架条件。[Google Play 测试要求](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en)

## 5. 构建、签名与更新

1. 四端拥有固定应用标识和统一产品版本，各自维护合法递增的 build number/versionCode；核心 ABI 和 Archive schema 独立版本化。
2. Windows runner 构建 Windows，Android runner 构建 APK/AAB，macOS runner 构建 Apple 产物。依赖锁定，输出符号与版本来源。
3. 普通验证任务不读取发布密钥。发布由受保护的流程触发，证书、profile、Keystore、口令进入受控 secret store，私钥另有加密离线备份与恢复演练。
4. 对正式构建保留 commit、依赖版本/许可证清单、安装包哈希、签名验证、公证或上传结果及验收记录。
5. 下载渠道为 HTTPS；更新只接受对应发布者的签名包。首期可用检查更新 + 用户安装，避免在四端各写一套不可靠的自动更新器。
6. 测试 N-1 → N 覆盖安装、正常退出/强退恢复和重复升级。安装包回退不等于数据可回退：升级迁移先备份，旧版不懂新 schema 时应拒绝改写并引导恢复备份。
7. 本地凭据不保证卸载后保留，按平台实际行为说明；升级应保持可用，换机应允许重新输入。用户自行导出的存档不被卸载流程删除。
8. 小范围更新仍维护证书到期、TestFlight 过期、API 模型变化的人工检查表与负责人；本轮不创建自动化任务。

## 6. 四端实施阶段

| 阶段 | 交付与退出条件 |
|---|---|
| R0 范围/环境 | 确认最低系统、发布地区、已有 Mac/开发者账号、签名渠道；固定四端能力表 |
| R1 四端技术验证 | 四端可调用共享核心；两手机真机话筒与后台测试；产出可安装签名样本；iOS ReplayKit 独立结论 |
| R2 共享核心 | 原版协议与数据规则迁移；同一组 token/Archive/SRT 样本四端通过 |
| R3 桌面完整版本 | Windows 原版功能全部对齐；Mac 逐步接入核心；旧版本和旧档可恢复 |
| R4 移动完整版本 | Android/iOS 麦克风、双语、存档、总结、分享、密钥与中断恢复完整 |
| R5 分发候选 | 非开发设备安装升级通过；Android 签名 APK、Windows 签名包、Mac 公证包、iOS TestFlight 可用 |
| R6 长期发布 | 相应正式渠道通过并实际可安装；维护、更新、支持和隐私页面上线 |

四端总量需要 R1 后重新估算。原 40～67 人日仅为桌面粗估，**不含新增 Android/iOS 完整客户端、四端签名流水线和正式渠道准备，不能继续用作整体承诺**。审核、账号验证与证书办理的日历等待时间另计。

## 7. 新增验收门槛

除桌面 A01～A18 外，新增：

| 编号 | 验收 |
|---|---|
| M01 | Android/iOS 真机连续话筒转写 60 分钟，并与前台 30 分钟基线比较；记录耗电、温度、队列、延迟，不先编造达标结果 |

| M03 | 拒绝/撤销权限、终止前台服务/广播、系统杀进程：不显示假录音，不擅自恢复采集 |
| M04 | Android 允许与禁止 playback capture 的两个受控测试源分别验证；不可采源给出真实结果 |
| M05 | 若纳入 iOS ReplayKit，验证扩展独立生命周期、内存/网络、主应用挂起和字幕落盘；否则发行说明明确未支持 |
| M06 | Android 大字体/TalkBack、iOS Dynamic Type/VoiceOver、竖横屏与小屏；主操作不被遮挡 |
| M07 | 四端互导 Archive，Mac legacy 导入，中文/日文/阿拉伯语文本，跨日/时区，SRT 无语义丢失 |
| M08 | 安装包与诊断包扫描无 API Key、私钥和录音；Key 替换/删除/换机行为符合说明 |
| M09 | 每平台至少一台未装开发工具的真实设备完成签名安装与升级；模拟器结果不代替 |
| M10 | 安装、升级、存档导出、服务失效与撤销凭据有使用文档；真实用户完成一轮无开发者辅助的操作 |
