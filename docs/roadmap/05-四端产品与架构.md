# 05 四端产品与架构

版本 v3 状态说明｜2026-09-16：本页保留 v2 的未来四端设计参考。当前首发仅 Mac/Windows，Mac 体验优先；Android 延后、iOS 暂缓，用户无 iOS 手机。以下手机“基础”均指未来重启该平台时的候选范围，不是当前承诺；以 [07](07-Mac优先的桌面实施方案.md) 为准。

## 1. 已确认目标

- 原项目在 Mac 开发，当前工作机为 Windows。
- 产品目标为 Windows、macOS、Android、iOS；具备实际签名、安装、升级和后续发布能力。
- 移动端以麦克风会议/课堂实时转写为基础，系统允许时支持其他应用音频。
- 首期个人和小范围使用，用户自填 Soniox/可选 DeepSeek API Key（BYOK），不提供统一付费额度。
- 延续此前的原生体验、核心共用和原有功能保留目标；本轮仍只写计划与文档。

新增范围不能把原 Windows 时间估算简单乘二，也不能把手机视作缩小后的桌面窗口。

## 2. 技术推荐与备选

| 路线 | 原 Mac 利用 | 四端共用 | 维护代价 | 适配本需求 |
|---|---|---|---|---|
| 原生界面 + Rust 核心 | 保留 SwiftUI 与原生音频经验 | 共享业务、数据、协议、算法；Apple 可共用部分 UI | C#/Kotlin/Swift/Rust 多语言，桥接和界面测试较多 | 推荐，最贴合此前原生体验要求 |
| Flutter + 原生音频适配 | 原 Mac UI 需逐步重写 | 可共用更多界面、应用逻辑 | Dart 加各平台原生插件；后台和系统录音仍要原生开发 | 若后续将单人维护效率排在原生控件之前，值得改选 |

Flutter 官方覆盖四个平台，但跨平台框架并不提供绕过音频权限或 Apple 构建要求的能力。[支持平台](https://docs.flutter.dev/reference/supported-platforms) · [平台集成与构建宿主](https://docs.flutter.dev/platform-integration)

当前不引入 Flutter 与多套原生 UI 并行长期维护。推荐先验证原生 + Rust 路线；若桥接成本超出资源，应在正式 UI 开发前重新决策。技术栈尚未冻结，方案不是已经实现的架构。

### 推荐模块

| 层 | 技术/责任 |
|---|---|
| Windows 客户端 | WinUI 3 + C#，WASAPI、窗口、电源、Windows 凭据 |
| macOS 客户端 | SwiftUI，现有 AVAudioEngine/ScreenCaptureKit 适配 |
| iOS 客户端 | SwiftUI，AVAudioSession/AVAudioEngine、文件分享、Keychain |
| Android 客户端 | Kotlin + Jetpack Compose，AudioRecord、前台服务、Android Keystore |
| Rust 核心 | PCM/时间线、Soniox 协议、字幕归并、存档/SRT、总结与可取消任务 |
| 绑定 | C# C ABI；Apple C ABI/XCFramework；Android JNI 薄层/NDK 库 |

核心不得引用桌面路径、窗口、Android Service 或 iOS App 对象。平台声明能力并传入持久化目录、生命周期事件、已取得的凭据和音频；核心发出可消费的状态与字幕事件。JNI 不在音频回调逐采样调用，保持块传输和有界队列。

网络连接和会话不能依附于 UI 页面对象：Android 由录音服务持有；iOS 由录音会话协调器持有；页面退出不应意外销毁正在进行的合法录音。后台运行许可始终由系统决定。

## 3. 平台能力矩阵

“基础”指计划交付并验收；“受限”指系统条件成立后支持；“验证项”不计入首期已承诺能力。

| 能力 | Windows | macOS | Android | iOS |
|---|---|---|---|---|
| 麦克风实时转写/翻译 | 基础 | 保留 | 基础 | 基础 |
| 其他应用播放音频 | WASAPI 播放端点受限采集 | ScreenCaptureKit 受限采集 | Android 10+ Playback Capture，受源应用策略限制 | ReplayKit 广播扩展独立验证，不承诺任意应用 |
| 系统音频 + 话筒混合 | 基础 | 保留 | 受限，需独立并发录音与设备验证 | 仅在获支持的捕获链路验证 |
| 切后台/锁屏继续话筒 | 桌面生命周期 | 桌面生命周期 | 前台录音服务与通知 | 正确 audio 后台模式与音频会话，需真机验收 |
| 通话/系统强占音频后恢复 | 设备事件 | 设备事件 | 中断并标明缺口，条件允许再恢复 | 服从 interruption 与系统可恢复状态 |
| 系统杀进程后自动继续录音 | 不作无条件保证 | 不作无条件保证 | 不承诺；恢复存档并让用户重新开始 | 不承诺；恢复存档并让用户重新开始 |
| 悬浮在其他应用上方显示字幕 | 原生置顶 | 原生置顶 | 可另评估悬浮窗权限，非基础 | 不承诺通用跨应用悬浮字幕 |
| 双语、Speaker、语言设置 | 基础 | 保留 | 基础 | 基础 |
| 多段存档、拆段、SRT、三种总结 | 基础 | 保留/接入 | 基础 | 基础 |
| 文件导入导出 | 本地对话框 | 本地对话框 | 文档选择器/分享 | 文件选择器/分享 |
| 自动云同步 | 首期无 | 首期无 | 首期无 | 首期无 |

Android 官方要求用户授予录音和 MediaProjection 权限，捕获与播放应用处于同一用户配置，源应用的 usage 与 capture policy 允许被捕获；撤销授权时必须停止，不可把持续静音当作仍正常录音。[Android Playback Capture](https://developer.android.com/media/platform/av-capture)

iOS 的 AVAudioSession 录音类别配合 audio 后台模式支持继续录音，但系统中断与终止仍需处理。具体 category 需按场景选择：`record` 会抑制其他输出，不应为“兼容其他应用播放”盲目采用；需验证 `playAndRecord` 等配置的实际音频路由。[Apple 录音类别](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/record)

ReplayKit 与 Broadcast Upload Extension 是系统提供的捕获机制。它们不能被当作 WASAPI 的等价通用实现。若以后验证跨应用音频，需要用户启动广播、独立扩展处理采样，并验证主应用挂起、扩展终止、无音频源等状态。[ReplayKit](https://developer.apple.com/documentation/replaykit) · [Broadcast Sample Handler](https://developer.apple.com/documentation/replaykit/rpbroadcastsamplehandler)

## 4. 手机交互与运行规则

- 首页只呈现本机可用输入；主按钮为开始/停止，正在使用的输入和发送到云端的状态可见。
- 竖屏原文/译文上下排列，横屏和平板可双栏；字号、Speaker、时间和滚动提示沿用桌面语义。
- 底部可分“录音、存档、设置”；总结在当前存档内展示，避免把手机变成多栏桌面。
- 首次使用功能时申请对应权限，拒绝后保留存档阅读/导出；不能启动“录音中”假状态。
- Android 使用 microphone/必要时 mediaProjection 类型前台服务，在允许的用户操作上下文启动，通知提供停止入口；不靠开机广播偷偷恢复。[前台服务规则](https://developer.android.com/develop/background-work/services/fgs/service-types)
- iOS 验证来电、Siri、耳机拔插、锁屏、后台、屏幕关闭和系统中断。中断时完成检查点，恢复依赖系统状态与用户录音意图；不照搬桌面“唤醒就重启”逻辑。
- 断网时首期不保存原始音频，因此不能承诺离线录音后完整补传。保留已收到的文字并标记缺口；将来若增加离线录音需单独授权和数据策略。
- 自动 SRT 首先保存在应用可写目录，导出/分享交由用户；不承诺任意写入手机公共下载目录。
- 长录音禁止把整场音频留在内存。对字幕显示做虚拟化，对存档做分段检查点；测量实际耗电与发热后再确定 UI 刷新频率。

## 5. 跨端数据与凭据

继续使用版本化 Archive v2 与旧 Swift 导入规则。四端使用同一组测试样本检验 UUID、日期、条目、segment 和 SRT 语义。导入时按副本与冲突策略处理，不通过网络自动同步。

Key 仅保存在当前设备的系统保护存储；Android Keystore 保存加密密钥，API Key 保存为其加密的密文，不能声称 Keystore 直接存任意文本。移动备份策略排除不可迁移的凭据密文，换机后要求重新输入。iOS Keychain 的可访问级别需兼顾用户主动开始后的锁屏录音，按最小权限验证，不打开云端同步。

首期客户端直接连接官方 Soniox/DeepSeek HTTPS/WSS 地址。用户自填 Key 是本地客户端使用，不把开发者共用主 Key 打进安装包。若将来改成运营方提供服务，则新增后端鉴权、限额与临时凭据发放；不能把那套后台当作 BYOK 首期必要条件。

## 6. Windows 主工作机与 Apple 构建

| 工作 | 当前 Windows | 额外环境 |
|---|---|---|
| 文档、核心逻辑、Windows 开发与验收 | 可以 | Windows 真机 |
| Android 编译、模拟器、签名 | 可以安排 | Android 真机，模拟器不能证明系统音频/耗电表现 |
| Mac/iOS 源文件编辑 | 可以编辑 | 编译/运行需 Apple 工具链 |
| macOS/iOS 构建、签名、模拟器 | 当前本机不能独立完成 | 可用 Mac 或受控 macOS CI 节点，合适 Xcode |
| Apple 真机录音与签名安装 | 不能由代码审阅代替 | Mac + iPhone；iPad 支持需另测 |

可优先复用原 Mac，但目前仅知道项目在那里开发过，未确认现在是否可远程访问、系统能否运行要求的 Xcode、是否已加入开发者计划。不得将这些条件写成已经具备。Apple 上传必须满足发布时的 SDK/Xcode 要求，最低部署版本与构建 SDK 是两回事。[上传要求](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds) · [近期要求](https://developer.apple.com/news/upcoming-requirements/)

## 7. 推荐验证顺序

v3 取代原顺序：先核验当前 Mac 功能和体验，在原项目上完善；随后完成 Windows 功能对齐及两端发布。当前不建移动样本或共享核心桥接工程。待桌面稳定且用户决定启动移动端后，重新验证本页平台规则与技术选型。
