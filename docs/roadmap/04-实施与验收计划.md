## 2. 必须验证的技术关口

- **G1 双平台调用**：C# 与 Swift 都能调用共享核心，取消/退出后不再收到回调，无跨边界内存泄漏。
- **G2 音频时间线**：不同采样率、两路启动错位、缺块、长时漂移均有可解释结果。若目标设备无法稳定捕获，先更新平台适配方案，不跳过问题进入 UI 完成宣告。
- **G3 原版语义对齐**：用已脱敏的服务消息与旧 Archive 样本比较，不仅依据 README 判断兼容。
- **G4 发布可用**：在未安装开发工具的机器完成启动、采集、保存、升级；构建成功不等于安装可用。

## 4. 性能目标与测量办法

下列是拟定验收目标，不是当前性能结论。

- 云端延迟：从对应语音结束到 UI 首次显示的 p50/p95，原文与译文分开；先记录 30 分钟固定语料。健康网络下暂以最终原文 p95 ≤3 秒、译文 p95 ≤5 秒为产品目标，P1 根据服务特性校准。
- 本地延迟：收到服务消息到 UI 更新 p95 ≤150 ms。与云端等待分开统计，避免把网络问题误判为界面慢。
- CPU/内存：在记录配置的基准机器连续录音 2 小时；区分音频队列、字幕数据及 UI 缓存。总占用允许随存档内容变化，音频队列和 UI 缓存必须有界。
- 交互：开始/停止即时反馈，实际收尾另显示状态；离线故障不阻塞窗口操作。
- 费用：不猜测小时费用。后续按服务当期价格、实际会话时长与总结 token 使用量建立估算表，并注明来源日期。
