# 07 Mac 优先的桌面实施方案

版本 v3｜2026-09-16｜本页为当前计划，取代此前冲突的两端/四端排期与架构前置条件。本轮仅修订文档，不开发应用。

## 1. 优先级与首发完成定义

| 顺序 | 目标 | 当前范围 |
|---|---|---|
| P0 | Mac 体验最优先 | 保留现有原生交互，验证并完善录音、字幕、恢复、存档与发布 |
| P1 | Windows 完整可用 | 原生实现现有主要功能，兼容 Mac 数据，完成签名安装与升级 |
| 后续 | Android | 保留麦克风优先的需求，不进入本轮开发或验收 |
| 暂缓 | iOS | 用户没有 iOS 手机，保留需求，不排开发、真机、签名或审核任务 |

首期为个人和小范围 BYOK 软件，无需先建账号、付费、云同步后台。完成 Mac/Windows 体验及发布门槛即可认定桌面首期完成，不以四端发布或共享同一代码库为条件。Mac 达标可先发版本，无需等待 Windows；Windows 的可行性工作可在不改变 Mac 的前提下开展。

## 2. 架构调整：保留 Mac，渐进共用

### 当前建议

- **Mac：继续 Swift/SwiftUI。** 在原项目中针对已确认问题做小步改进，保留现有音频链路、原生窗口和操作习惯；不先整体重写 UI 或替换业务引擎。
- **Windows：WinUI 3 + C#。** 按原项目功能规范实现 Windows 采集、字幕、存档、总结与生命周期，结构上分层，不复制大型 ViewModel 的耦合。
- **首期共用契约和测试资产。** 统一字段语义、时间规则、请求参数、字幕样本和 SRT 预期结果。暂时维护两套业务实现是明确接受的代价，不宣称已经共享代码。
- **Rust 是后续可选重构。** 两端稳定后，只有确定可减少维护成本且 Mac 无体验回退时，才逐模块提取纯逻辑；先考虑格式转换/导出等可独立验证的模块，音频与会话协调最后评估。

此调整响应“Mac 体验最优先”，没有取消未来跨平台愿景。当前不为未来手机提前引入 JNI、XCFramework、移动后台抽象，也不为了框架统一重做 Mac 界面。

### 控制双实现差异

每个功能维护来源与验收编号；规则变化时更新共同样本及两端结果。平台权限/设备恢复差异单独标记，数据语义不得静默分叉。若将来抽取共享模块，需要有迁移前后输出比较和回退方案。

## 3. Mac 体验保障

先建立“当前可用版本”基线，再讨论改善，不能根据静态源码直接判定用户已有体验一定存在问题。

| 维度 | 基线与验收方式 |
|---|---|
| 主流程 | 从开始录音到查看字幕、停止保存、接续存档的操作不增加无必要步骤 |
| 字幕阅读 | 保留原文/译文、时间、Speaker、跨天日期、新内容提示；翻译更新不造成跳行或打断阅读 |
| 音频完整性 | 电脑/话筒/双输入、录音中切换、首句缓冲、尾句收齐按固定用例验证 |
| 长时间使用 | 至少 2 小时录音，记录 CPU、内存、延迟与 UI 响应，与同设备旧版比较；无持续队列堆积 |
| 生命周期 | 合盖/唤醒、设备变化、断网、用户停止后不误恢复；状态与实际采集一致 |
| 原生交互 | 主题、菜单、快捷键、置顶、保存面板与文本选择按 Mac 习惯验收；不移植 Windows 控件行为 |
| 数据安全 | 原有存档可读、接续和导出；升级前备份；恢复策略实际演练 |
| 发布体验 | 新机器可验证签名安装；正式分发完成相应签名、公证、升级验证与使用说明 |

性能以相同硬件、网络、语料、模型和时长对比，云端波动与本地开销分开记录。任何可复现的字幕丢失、卡顿、恢复失败或数据错误都阻止该 Mac 改动发布；不要用代码共用率解释体验回退。尚无 Mac 实测数据，不预填通过结果。

## 4. 首期数据与密钥策略

1. 保留现有 Mac Archive 格式和目录，不要求为 Windows 推出强制 v2 迁移。
2. Windows 建立 legacy 兼容层，正确处理 Swift 日期、可选字段、UUID 和跨段时间；新 Windows 存档优先按已验证的兼容格式写出，内部模型仍可用中性字段名。
3. 使用原 Swift 编码器生成样本，实测 Mac → Windows → Mac 导入，核对段数、文本、时间和 SRT；未通过前不声称双向兼容。
4. 对 legacy 无法表达的额外信息暂不写入共享存档；必要时保存独立平台设置，避免旧 Mac 重写后丢失新字段。未来 schema 升级单独评审、备份、迁移和回退。
5. Mac 凭据可在发布完善阶段从 UserDefaults 渐进迁移至 Keychain：先验证读取和新保存成功，再处理旧项；失败时保持可恢复，不静默丢 Key。Windows 使用系统保护存储。Key 不进入导出和跨端样本。

## 5. 执行阶段

| 阶段 | 工作与交付物 | 退出条件 |
|---|---|---|
| D0 Mac 基线 | 固定原版本、功能/交互记录、旧档样本、问题清单、Mac 构建环境核验 | 用户实际使用路径有依据；区分问题与新增想法 |
| D1 Mac 完善 | 按问题逐项修复和发布准备，保留可回退版本 | Mac 体验矩阵通过；可先交付 Mac 版本 |
| D2 Windows 实现 | 先音频/服务最小链路，再按功能表补齐原生 UI、保存、总结、恢复 | 原版功能对齐；Windows 音频和数据测试通过 |
| D3 桌面互通与发布 | 双向存档、非开发机安装、升级、签名、公证及支持文档 | 两端各自可实际安装使用与更新；Mac 无回退 |
| D4 后续评估 | 是否抽取共享代码、是否启动 Android | 由后续需求与维护成本决定，不阻塞桌面完成 |

D0 必须先建立 Mac 基线；D2 的独立 Windows 工作无需等待所有 Mac 改善完成，但不能占用或改动尚未验证的 Mac 主版本。具体日历排期在 D0 与 Windows 音频验证后估算；旧 40～67 人日包含不同重构路线，保留作历史，不沿用为当前承诺。

## 6. 环境与发布条件

当前 Windows 足以开展 Windows 实现、文件格式检查和文档工作。Mac 构建、原生交互、设备音频和睡眠恢复需要可用 Mac；远程构建产物只能证明构建结果，不能替代真实设备体验验收。

原 Mac 是否仍可使用、具体硬件与系统、现有发布账号/证书尚未核验。它们影响后续 Mac 执行和分发，不妨碍当前方案完成。没有 iPhone 是已知情况，只影响未来 iOS 阶段，不影响 Mac。

继续沿用 06 的 Mac/Windows 签名和长期分发要求。首期不注册 Android/iOS 发布任务，不以商店审核作为桌面唯一分发渠道；具体渠道按现有资质选定并实测。依旧不把“计划支持签名”写成“已经签名上线”。
